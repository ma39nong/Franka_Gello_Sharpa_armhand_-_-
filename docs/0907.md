# 2026-09-07 数据采集联调记录

本文简要记录本轮对话中完成的数据采集改动、设计结论和现场排查结果，供后续采集与维护参考。

## 1. 当前采集流程

遥操与采集仍保持两个独立终端、两个独立进程：

```text
终端 1：Wuji + GELLO 遥操及 Operator UI
终端 2：三相机、手部只读 telemetry、rosbag 采集器
```

Operator UI 现在可以连接独立采集器：录制按钮在“开始录制”和“停止并校验”之间按状态切换，快捷键为 `L`；“丢弃最近一次”的快捷键为 `A`。原先左右 `Start arm` 的 `L/A` 快捷键已取消，只保留 GUI 按钮。采集终端原有的 `SPACE`、`D` 快捷键继续保留。UI 只通过本机 `127.0.0.1:5592` 控制采集状态，不合并进控制链，采集器或 UI 故障不会接管或阻塞遥操。

在线阶段只保存 ROS bag，停止录制后进行完整性校验，但**不会自动转换为 LeRobot**。确认 bag 为 `finalized` 后，再手动运行转换器。

## 2. 相机与数据量调整

- 左右臂相机 `cam1/cam2`：由 `1280×800` 降为 `640×480`，保持 30 Hz RGB。
- 头部相机 `cam0`：RGB 和原始深度均为 `640×400 @ 20 Hz`；深度保持 Y16 原始值，不做 D2C、点云或在线对齐。
- rosbag 默认 QoS 使用 `reliable + keep_last + depth 10`。
- rosbag 写缓存设为 256 MiB：`--max-cache-size 268435456`。

`DDS queue depth=10` 表示订阅端最多保留最近 10 条尚未处理的消息，不代表 10 Hz，也不是 10 ms。理想周期与频率的关系为：

```text
周期(ms) = 1000 / 频率(Hz)
20 Hz ≈ 50 ms；30 Hz ≈ 33.3 ms；100 Hz = 10 ms
```

报告里的较大 `ms` 通常是最大消息间隙或抖动，而不是平均周期。增加 DDS depth 或 rosbag 缓存只能吸收短时堵塞，无法修复相机未出帧、USB 带宽不足、进程调度停顿或源端本身断流。

## 3. 校验时间戳设计

ROS bag 同时保留两套时间：

- `source header time`：消息在相机、控制或 telemetry 源端产生的时间。
- `bag receive time`：rosbag 实际收到并写入该消息的时间。

新规则将二者分开使用：

1. 消息数、频率、单调性和内部连续性以 source 时间判断，这是数据内容是否真实连续的主要标准。
2. bag receive time 出现大间隙时记录为 `transport_warnings`，用于提示 DDS、CPU、USB 或磁盘写入阶段曾发生拥塞；若 source 时间仍连续，不再因此把 episode 直接判坏。
3. 录制窗口的首尾覆盖仍参考 bag receive time，避免设备时钟与主机接收时钟的固定偏移造成错误边界判断。
4. 报告同时保存 source/bag 的消息数、首末时间、频率、最大 gap 和非单调计数，便于区分“源数据断流”和“传输延迟”。

对应增加了合成测试：模拟 bag 接收侧发生约 250 ms 堵塞、但 source 仍保持正常周期，确认校验器只产生传输告警，转换结果仍按 source 时间正确排序和对齐。

### 传输告警的含义

`transport_warnings` 不等于数据必然丢失。它表示 rosbag 接收时间轴不平滑，需要结合 source 报告判断：

- source 连续、内容完整：episode 可以通过，但应关注系统负载和 USB/磁盘余量。
- source 同时存在超限 gap、缺消息或非单调：属于真实数据问题，应判为 incomplete 或重新采集。

## 4. 首尾无效区间裁剪

采集任务开始后的前 1 秒、结束前的后 0.2 秒作为操作缓冲区：

- 原始 ROS bag 始终完整保存，不截断、不改写数据库。
- 校验器在 required streams 的 source 公共区间上排除开头 1 秒和结尾 0.2 秒，再判断有效区间连续性和 engagement。
- 位于缓冲区内、超出普通边界容差的缺口单独记为 `boundary_warnings`。
- LeRobot 转换器使用同一 source 公共区间和裁剪规则，并将裁剪后的训练时间戳重新从 0 开始。
- 如果 episode 太短，裁剪会移除全部有效区间，校验或转换会明确失败。

默认值位于 `data_collection/config/record_gello.yaml` 和 `data_collection/config/convert_gello_lerobot_v2.yaml`，均为：

```yaml
trim_start_sec: 1.0
trim_end_sec: 0.2
```

## 5. LeRobot 转换与重校验

转换器已调整为：先按 source header 重新排序各流，再取公共有效区间，以 30 Hz 构造确定性训练时间线；对每一时刻只选择不超过 150 ms 的最新历史样本，不使用未来样本。RGB 不插值，cam0 的 20 Hz 图像和深度帧只存一次，由数据行按时间引用。

旧 bag 可以独立重校验。重校验只原子更新 `collection_state.json`，不会修改 `.db3` 或 `metadata.yaml`：

```bash
./ops/run/revalidate_recording.sh \
  /home/user/franka_teleop_data/bags/gello/episode12 \
  --trim-start-sec 1 --trim-end-sec 0.2
```

手动转换命令：

```bash
./ops/run/convert_recording.sh \
  /home/user/franka_teleop_data/bags/gello/episode165 \
  /home/user/franka_teleop_data/datasets/episode165
```

转换只接受 `finalized` bag，先写相邻临时目录，完整验证通过后再原子发布正式目录，失败不会修改源 bag，也不会留下对外可见的半成品数据集。

## 7. 启动与 READY 门禁

早期出现过采集器先打印 `READY`，相机随后仍继续初始化的情况。现在启动状态分为：

```text
WAITING → READY → RECORDING → STOPPING/VALIDATING → FINALIZED 或 INCOMPLETE
```

采集器不再只检查 ROS graph 上是否存在 topic，而是等待所有 required topic 收到真实、类型正确且新鲜的消息，并连续稳定 2 秒后才显示 `READY`。因此看到 `Still waiting for required topics` 时不要开始动作，应按提示检查具体 stale/missing 流。

Orbbec 的 `Initialize device cost: xxxx ms` 是相机 SDK 自身初始化耗时。只要这些日志出现在 `READY` 之前就是正常的；新的门禁保证相机完全出帧后才允许开始录制。

## 9. 手 telemetry invalid packet 修复

`Home Both Arms` 附近可能用同一份缓存手反馈生成新的 telemetry envelope，导致连续两包的反馈时间戳相同或倒退。旧逻辑会用零或负 `dt` 计算速度，从而把整包判为 invalid。

当前处理方式：

- 时间戳重复或倒退时，不再计算本次速度。
- 该侧速度估计器重新建立基线，状态标记为 `unavailable_nonmonotonic_reset`。
- position、command 和 status 仍然保留，不因速度暂时不可用而丢掉整包。
- 下一条新鲜时间戳到来后恢复有限差分速度。

另外，telemetry 的 dropped/lost/duplicate/out-of-order/stale/invalid 计数属于接收器进程生命周期累计值。校验器现在记录 `first/last/max/delta`，只以本 episode 内的实际增量 `delta` 判定失败；录制开始前已经产生、录制期间未继续增长的历史错误不会污染后续 episode。episode161 已使用新规则重校验为 finalized。

## 10. 现场故障结论

### 相机或采集器无法启动

- `Address already in use`（UDP 5602）：已有 hand telemetry receiver 或旧采集容器未退出，需要先结束占用进程。
- `127.0.0.1:5592 already in use`：已有采集控制服务运行，不能重复启动第二个采集器。
- OrbbecViewer、compose `orbbec` 与三相机采集互斥，启动脚本会主动拒绝资源冲突。
- cam2 一度在 OrbbecViewer 中也不可见，换 USB 口后恢复，说明当时更接近 USB 端口、供电、带宽或枚举问题，而不是代码回退导致。
- 只有 topic 名而没有新鲜消息时仍会停在 WAITING，这是保护机制，不应绕过。

### rosbag 缓存不是根治手段

缓存从小改大只能缓解短时写盘抖动。若 cam0 的 source 时间正常、仅 bag receive gap 较大，应优化磁盘、CPU 调度、DDS 和 USB 拓扑；若 source 自身也断流，则应优先处理相机链路，继续增大缓存意义有限。
